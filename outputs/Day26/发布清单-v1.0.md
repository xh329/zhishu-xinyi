## 一、版本标记

| 类型 | 位置 | 内容 |
|---|---|---|
| 机器可读 | 5 个页面 `<head>` | `<meta name="app-version" content="1.0.0" />` |
| 肉眼可读 | `index.html` 页脚 | `栀子微光，伴你读完这一段 ｜ v1.0`（`.foot-ver`，极小、低对比、同色系） |

**为什么版本标记是硬要求，不是装饰**：

> WorkBuddy 静态托管**没有版本历史**，「回退」只能靠「把上一版产物重新发布」。
> 如果两版产物在页面上看不出差别，就**无法证明回退真的生效了**——你只能"相信"它生效。
> 所以发布物必须自带一个能从外部读到的版本标识，让回滚从"感觉"变成"验证"。

核验命令（任意机器、任意时刻都能跑）：

```bash
node outputs/Day26/release.cjs check https://zhishu-xinyi.app.workbuddy.host/
# 输出里会直接给：版本标记（meta=1.0.0 / 页脚=v1.0）+ 总指纹 + 与本地产物逐文件比对结论
```

## 三、发布步骤（照抄）

1. **跑检查**：`node skills/verify-project/verify.cjs` → 必须 10/10、退出码 0；不通过就停下修，别发。
2. **构建产物**：`node outputs/Day26/release.cjs build` → 期望 22 个文件、版本标记 `v1.0`。
3. **归档线上现版**（若线上已有版本）：`node outputs/Day26/release.cjs archive <URL> outputs/Day26/versions/<旧版本号>`。
4. **发布**：用「发布为应用」把 **`outputs/publish-site`** 这个目录发布出去。
   - ⚠️ 必须用**同一个目录**发布：托管是"按目录认领应用"的，换目录会新建一个应用、**分享链接会变**。
   - 发布是**覆盖式**的：链接不变，线上内容被替换。
5. **记时并留证**：记下发布时刻；紧接第四步的验证，别隔夜。

## 五、代码与数据备份方式

按"回滚真正要用哪个"排序，而不是按"哪个听起来专业"：

| 顺位 | 备份什么 | 方式 | 用途 |
|---|---|---|---|
| 1 | **代码** | git 提交 + `git tag v1.0` + 推 `origin/master`（异地） | 任何时候都能重建任意版本的源码 |
| 2 | **发布产物** | `release.cjs build` 可重建；产物归档到 `outputs/Day26/versions/<版本>/` + `MANIFEST.md`（逐文件 sha256） | **回滚真正用的是这个** —— 静态托管没有版本历史 |
| 3 | **线上现版快照** | `release.cjs archive <URL> <目录>`（**发布前做**） | 万一新版有问题，手上有上一版的完整字节 |
| 4 | **用户数据** | 浏览器 `localStorage`；**服务端无数据可备** | 已知边界：换浏览器/清缓存即丢，要保数据需接回云端 |

**两条纪律**：

- **没有演练过的备份等于没有备份。** 本次 Day 26 做了真实回退演练，实测耗时见《回滚演练记录.md》。
- **产物归档要带指纹**（`MANIFEST.md`），否则你无法证明"归档的这堆文件"与"当时线上跑的那版"是同一版。
