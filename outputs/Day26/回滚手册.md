# 栀书心驿 · 回滚手册

> Day 26 板块②③④。目的：**出事的时候不用思考，照着念就能退回去。**
> 分两条路径：静态托管（本次已真实演练）、云函数与数据（本轮不实操，只备查）。

## 零、先记住一件事

> WorkBuddy 静态托管**没有版本历史**。
> 所以这里的"回退"不是点一个按钮回到上一版，而是：**用上一版产物，重新发布一次**。
> 推论：**上一版产物必须提前归档在手边**，否则真要退的时候你无版可退。

## 一、触发条件

### 1.1 「什么情况必须回滚」判断表（余力加练）

**门线只有一条：用户还能不能正常用。**
能用的小瑕疵不发回滚；不能用的一律回滚，**不现场抢修**（线上抢修 = 无验证的改动，最容易越修越坏）。

| # | 情形 | 可观测判据（别靠感觉） | 判定 | 处置 |
|---|------|------------------------|------|------|
| 1 | 首页打不开 / 白屏 | `curl -s -o /dev/null -w "%{http_code}" <URL>` ≠ 200，或拿到的 HTML 里没有 `<title>` | 🔴 **立即回滚** | 走 §二，退到上一版 |
| 2 | 关键资源 404（css/js 断链） | `release.cjs check` 报 `✗`；或 F12 里 `style.css` / `*.js` 404 | 🔴 **立即回滚** | 走 §二 |
| 3 | 关键流程断（收书 / 写心得点了没反应） | F12 控制台有红报错，或动作后书架无变化 | 🔴 **立即回滚** | 走 §二 |
| 4 | 线上版本标记与预期不符 | `release.cjs check` 打印的版本标记 ≠ 你刚发的版本 | 🟠 **先确认**：可能是发布没成功/发错目录 | 确认后再决定回滚；若确为串版，回滚到已知好版本 |
| 5 | `check` 报"不一致"但页面正常 | 逐文件差异集中在**文档/注释**这类不影响运行的改动 | 🟡 **不回滚** | 记录，纳入下次发版 |
| 6 | 只是文案/间距/配色不好看，页面可用 | 人工目视 + 流程能跑 | 🟡 **不回滚**（P2） | 记入下次发版清单 |
| 7 | 怀疑是缓存导致"看起来没生效" | 带 `?v=<时间戳>` 复取同一 URL，内容变了 | 🟢 **缓存假象，别回滚** | 只做缓存说明；`check` 脚本已内置破缓存参数 |
| 8 | 数据异常（书架/心迹内容错了、丢了） | localStorage 里 `zhishu_books` / `zhishu_notes` 内容不符预期 | ⚫ **回滚解决不了** | 代码回滚不动数据；走 §五 数据恢复 |
| 9 | 页面可用但慢 | 首次内容渲染明显变慢，仍能操作 | 🟡 不回滚 | 记录待优化 |
| 10 | 发布后才发现发的是旧产物 | `check` 的版本标记显示还是上一版 | 🟠 重发正确产物 | 不用回滚（线上本来就是旧的） |

**回滚决策三条硬规矩**：

1. **先备份，再动手。** 回滚前先把线上现状归档（`archive`），否则你连"退回哪里"都没锚点。
2. **回滚是完整动作，不是半截。** 退回去 → **必须验证** → 才算回滚完成。
3. **回滚不等于修好。** 回滚只是止血；根因定位与修复回到本地做，下次发版带回去。

### 1.2 回滚决策图

```
出事
 ├─ 用户还能正常用吗？ ── 能 ──→ 记入下次发版清单（不回滚）
 │                         └─ 不能
 ├─ 是数据问题（内容错/丢）？ ── 是 ──→ 走 §五 数据恢复（回滚代码无用）
 │                          └─ 否
 ├─ 先 archive 归档线上现状（备份！）
 ├─ 把上一版产物放进 outputs/publish-site/ → 重新发布同一目录
 ├─ check 验证：版本标记 == 上一版？
 │     ├─ 是 → 回滚完成，记耗时、记根因待办
 │     └─ 否 → 检查①发布目录是否同一个 ②是否缓存 ③归档产物是否完整
```

## 二、静态托管回退步骤（✅ 本次已实测，见《回滚演练记录.md》）

### 2.1 前置条件

- `outputs/Day26/versions/<上一版>/` 存在，且含 `MANIFEST.md`
- 知道**上次发布用的是哪个目录**（本项目 = `outputs/publish-site`，全程不许换）

### 2.2 步骤（照抄）

```bash
# ① 先归档线上现状 —— 哪怕再着急，这一步别跳（否则没有锚点）
node outputs/Day26/release.cjs archive <站点URL> outputs/Day26/versions/<现场版本号>

# ② 把上一版产物放回发布目录（先清空，避免新旧混杂）
#    PowerShell：
#      Remove-Item outputs\publish-site\* -Recurse -Force
#      Copy-Item outputs\Day26\versions\v0.9\* outputs\publish-site\ -Recurse -Force
#    （MANIFEST.md 不要拷进发布目录，它只是归档说明）

# ③ 确认目录里已是上一版
node outputs/Day26/release.cjs fingerprint outputs/publish-site
#    期望：版本标记 =「（无版本标记 = 上次发布留下的旧版）」或旧的版本号

# ④ 重新发布同一个目录（用「发布为应用」发布 outputs/publish-site）
#    —— 覆盖式发布，分享链接不变

# ⑤ 验证（这一步不做，回滚不算完成）
node outputs/Day26/release.cjs check <站点URL>
#    期望：线上总指纹 == 本地产物总指纹，且版本标记 == 上一版
```

### 2.3 恢复 v1.0（回滚演练的收尾，也是真出事后的收尾）

```bash
node outputs/Day26/release.cjs build           # 从仓库重建 v1.0 产物（先清空再复制）
node outputs/Day26/release.cjs check <站点URL>  # 重新发布该目录后验证
#    期望：✅ 一致 + 版本标记 v1.0
```

### 2.4 实测耗时（2026-10-12 演练）

| 环节 | 实测 |
|------|------|
| **退回上一版**（备份 → 换产物 → 重新发布 → 验证通过） | **86 秒**（其中不含备份的"决定回退 → 验证通过"为 **37 秒**） |
| **恢复 v1.0**（重建 → 重新发布 → 验证通过） | **45 秒** |

详细逐步耗时与判定证据见《回滚演练记录.md》。

### 2.5 静态回退的坑（本次踩到/预判到的）

| 坑 | 后果 | 规避 |
|---|---|---|
| **换了发布目录** | 托管按目录认领应用 → 会新建一个应用，**分享链接变了**，旧链接还活着且内容陈旧 | 全程固定 `outputs/publish-site`；演练前后都确认链接没变 |
| **发布目录里残留旧文件** | 新版产物不完整也可能"看起来正常"，旧文件冒充新版 | `build` 脚本**先清空再复制**；必要时人工 `ls` 核对文件数（应为 22） |
| **缓存假象** | 明明回退了，页面还是新版，误判"回滚失败" | 带 `?v=<时间戳>` 复取；`check` 脚本内置破缓存 |
| **两版产物肉眼无差别** | 无法证明回滚是否生效 | 发布物自带版本标记（页脚 + meta）；没有它就别做演练 |
| **回滚时顺手改了别的东西** | 回滚这个"已知安全操作"变成新的未知改动 | 回滚期间**只换产物，不改内容**；要改就回本地改 |

## 三、云函数回退步骤（⏸ 备查，本轮不实操）

> 现状：本项目的云函数（`books` / `notes` / `health`）与 MySQL 在 Day 20–21 已不可用
> （apigw 域名被回收、DNS 解析不到），当前站点是纯静态版。本节仅作为将来重新接回后端时的备查。

**回退步骤（CloudBase）**：

1. **先看清在退什么**：确认是"代码"还是"环境变量"还是"数据"出了问题——三者回退方式完全不同。
2. **代码回退**：CloudBase 控制台 → 云函数 → 选中函数 → 版本管理 / 历史版本 → 回滚到上一个正常版本；
   或者用 CLI 重新部署 `git tag` 对应的代码目录（`cloudfunctions/books`、`cloudfunctions/notes`、`cloudfunctions/health`）。
3. **环境变量**：⚠️ 控制台里改环境变量是**整体覆盖**（Day 20 踩过：只填新变量会把旧变量清空）。
   回滚代码时**不要顺手动环境变量**；确要改，先抄下现有全部键值。
4. **部署后验证**（缺一不可）：
   - `curl <API>/health` → 200
   - `ALLOWED_ORIGIN` 白名单包含当前静态托管域名（否则跨域被拦）
   - 重跑 Day 22 的 55 项 SQL 回归 + Day 23 的 16 项错误文案自检
   - 真实读写一条：`GET /api/books`、`POST /api/notes` 各一次

**为什么本次不做**：课程边界（本轮只做静态托管回退）。而且云函数当前不可用，做了也没有观测对象。

## 五、数据恢复（⏸ 备查，本轮不实操）

**本项目的数据现状（必须先说清）**：

- 用户数据（书籍、心得）存放在浏览器 `localStorage`（键名 `zhishu_books` / `zhishu_notes`）。
- **服务端没有任何用户数据**，因此"数据备份/回档"在当前形态下**不适用**。
- 已知边界：换浏览器、换设备、清缓存 → 数据不可见。要真正保数据，前提是接回云端后端。

**将来接回 CloudBase / MySQL 后的数据恢复步骤（备查）**：

1. **先导出再回档**：控制台 → 数据库 → 备份与回滚；回档前先把当前数据导出留一份（回档不可逆）。
2. **按时间点回档**：选择故障发生前的备份点，回档后**校验行数**与最近一次写入是否存在。
3. **红线**：数据恢复是**破坏性、不可逆**操作，必须二次确认；能靠"补一条正确数据"解决的，不要整库回档。
4. 数据库结构变更（DDL）**不随云函数回滚**，需要单独按迁移脚本退回。
