## 三、结论：这套流程敢不敢用

**敢用。数字摆在这：真出事时，86 秒能退回上一版并确认退成功了；45 秒能恢复新版。**
但它成立靠三个前提，缺一个就是"不敢用"：

1. **上一版产物必须提前归档在手。** 静态托管没有版本历史，没有归档就**无版可退**。
   （本次演练 1.1 之所以先花时间备份，就是因为这条是铁律。）
2. **发布物必须带可核验的版本标记。** 没有页脚 `v1.0` 这种肉眼可见的差异，
   你只能"相信"退回去了，不能"证明"退回去了 —— 缓存、串版都会骗人。
3. **发布目录从头到尾不能换。** 托管按目录认领应用，换了目录等于退到一个新链接上去。

**这次演练真实抓到的坑（不是白跑）**：

- 🔴 **历史遗留的双链接**：`https://zhishu-xinyi.app.workbuddy.host/` 是 10-11 一次临时发布会话留下的**另一个应用**（发布源在仓库之外的临时目录），至今仍在线上服务着旧内容。本次 v1.0 的正式链接是 `https://zhishu-xinyi-70127.app.workbuddy.host/`（发布源在仓库内、可复现）。
  → 风险：以后"更新了没生效"很可能是改错了链接；回滚时也可能退错应用。**建议尽快二选一**（保留仓库内这条，旧的那条下线或不再使用）。
- 🟡 回滚**不经过 git**：git 里没有任何"回滚提交"，回滚动作只发生在发布目录与托管之间。所以 git 历史看不出回滚，必须靠《演练记录》+ 产物指纹留档。
- 🟢 恢复后指纹与首发完全一致，证明"退回去 → 再回来"没有引入任何字节差异 —— 这正是回滚演练最该证明的一件事。
