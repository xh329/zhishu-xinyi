## 〇、动手前先回答「我的数据从哪来」（三个问题）

| 问题 | 栀书心驿的答案 | 结论 |
|------|----------------|------|
| 1. 数据是「别人产出的」还是「我的用户产出的」？ | books / notes 都是**用户自己录入**的书名与读书心得 | 用户产出 |
| 2. 只看当前，还是能回看过去？ | 心得要回看、书架要保留 | 要回看历史 |
| 3. 这份数据明天还在原地吗？ | 用户昨天的输入不存就没了 | 必须存进自己的数据库 |

**路由结论**：用户产出 → 必须存进我们自己的数据库 → 今天让接口从 `books` / `notes` 两表读出真实数据。
**所以**：模板里打卡 App 的 `/api/hot`(热搜) + `/api/favorites`(收藏) 对应到本项目就是 **`GET /api/books` + `GET /api/notes`**；我们**不去拉外部热搜 API**（那属于「别人产出」路线，本项目用不到）。

## 一、接口与表的对应关系（先讲清"对不上的地方"）

| 接口 | 读哪张表 | 返回字段键 | 契约条目 |
|------|----------|------------|----------|
| `GET /api/books` | `books`（核心表） | `books` | api-contract §三 第 2 项 |
| `GET /api/notes` | `notes`（记录表） | `notes` | api-contract §三 第 6 项 ★ |

**「接口返回的数据里，哪一项和你建的表对不上？怎么发现的？」**
字段名是一一对应的（`id/title/...` ↔ 表列），**对不上的是"类型表示层"**，不是字段名：
- 表里 `created_at` / `updated_at` 是 `DATETIME`（`YYYY-MM-DD HH:MM:SS`）；契约要求响应里是 ISO8601 字符串（`YYYY-MM-DDTHH:MM:SS`）。
- 表里 `mood` 是 `JSON` 列；契约要求响应里是 JS 数组（如 `["触动"]`）。
**怎么发现的**：把 `db/schema.sql` 的列类型逐列对比 `api-contract.md` §三 的响应示例，发现 `DATETIME` 不会自动变成 ISO 字符串——于是在 `cloudfunctions/*/db.js` 里写了 `toISO()` 做 `DATETIME→ISO` 转换，`mood` 由 mysql2 的 JSON 类型自动解析（并加了一层 `JSON.parse` 兜底）。这一步就是"对不上 → 在接口层补齐"。

## 二、部署步骤（CloudBase）

> 前提：本地已装 `Node.js` + 微信/腾讯云 `tcb` 命令行，且已登录 CloudBase 环境（envId）。
> 没有账号/凭据时无法在沙箱内代跑，以下命令在你本机执行即可。

### 2.1 建数据库并灌入真实数据
1. CloudBase 控制台 → 数据库 → 新建 **MySQL** 环境（或 TDSQL-C），记录连接信息。
2. 用任意 MySQL 客户端连上后执行：
   ```bash
   mysql -h <DB_HOST> -u <DB_USER> -p <DB_NAME> < db/schema.sql
   mysql -h <DB_HOST> -u <DB_USER> -p <DB_NAME> < db/seed.sql
   ```
   脚本可重复执行（schema 先 DROP 再 CREATE，seed 先 DELETE 再 INSERT），重跑不报错、数据幂等。
   此时 `books` 有 5 本、`notes` 有 6 段真实种子数据。

### 2.2 配置云函数环境变量（**密钥只走环境变量，不写进代码**）
在 CloudBase 控制台给 `books` 和 `notes` 两个函数各配置：
```
DB_HOST=...
DB_PORT=3306
DB_USER=...
DB_PASSWORD=...   # 仅环境变量，不落仓库
DB_NAME=zhishu_xinyi
```

### 2.3 部署两个云函数
```bash
# 在工程根目录（含 cloudfunctions/ 的目录）
tcb fn deploy books
tcb fn deploy notes
```
每个函数目录已自带 `package.json`（含 `mysql2` 依赖），CloudBase 会自动安装。

### 2.4 配置 HTTP 触发 + 路径映射
给两个函数开启 **HTTP 触发**，并把路径映射成契约里的路由：
```
books 函数 → /api/books
notes 函数 → /api/notes
```
部署完成后你会拿到形如 `https://<envId>.apigw.tencentcs.com/release/books` 的公网地址（实际路径以控制台为准）。

## 三、浏览器验证方法（交截图 #1：公网接口返回）

1. 打开浏览器，地址栏直接访问：
   ```
   https://<你的公网地址>/api/books
   https://<你的公网地址>/api/notes
   ```
2. 应看到（节选）：
   ```json
   { "ok": true, "books": [ { "id": "b_seed01", "title": "小王子", "user_id": "local", "created_at": "2026-09-28T09:10:00" }, ... ] }
   { "ok": true, "notes": [ { "id": "n_seed01", "book_id": "b_seed01", "content": "长大后才懂，玫瑰的骄傲不过是怕被辜负。", "mood": ["触动"], "user_id": "local", "created_at": "2026-09-28T10:00:00", "updated_at": null }, ... ] }
   ```
3. 截图要求：**地址栏可见公网地址** + 返回体里有真实条目（不是假数据）。
4. 余力加练验证：访问 `https://<地址>/api/notes?limit=3`，应只返回前 3 段。

## 四、"改一条数据库数据，确认接口跟着变"验证（交证据）

1. 用 MySQL 客户端改一行真实数据（例如把 n_seed01 的内容改掉）：
   ```sql
   UPDATE notes
      SET content = '改过之后再看，玫瑰的骄傲其实是怕被辜负。'
    WHERE id = 'n_seed01';
   ```
2. **不重部署、不刷新数据库**，直接在浏览器刷新 `https://<地址>/api/notes`。
3. 返回里 `n_seed01` 的 `content` 已变成新句子 → 证明接口读的是真库、且实时跟随库变化（这就是"用户产出 → 存自己库 → 接口直读"的价值）。
4. 也可反过来验证"删书级联"：`DELETE FROM books WHERE id='b_seed01';` 后，`/api/notes` 里该书两段心得也随之消失（外键 `ON DELETE CASCADE`）。

## 五、沙箱/无 CloudBase 时的最小验证（卡住降级）

若暂时没有 CloudBase 环境，先用 `outputs/Day17/self-check.js` 在 Node 里**真正执行**两个云函数（用 mock 的 mysql2 注入假数据），验证：SQL 字符串与参数是否参数化、响应形状是否 `{ok, books/notes}`、405 / 500 错误路径是否正确、DATETIME→ISO 与 mood 解析是否对。

```bash
node outputs/Day17/self-check.js
```
全部断言通过即代表"接口 SQL 在控制台验证正确"，剩下只是把同样的逻辑部署到 CloudBase 并指向真库。

> 真实数据源（CloudBase MySQL）不可用时的降级：保留 seed 数据、在页面标注「示例数据」、记入待办；接口本身先按本节能在控制台验证 SQL 正确，再排查部署环节。
