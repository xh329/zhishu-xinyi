# Day 24 · 修一个真实 Bug 的全证据链（复现 → 定位 → 修复 → 验证）

> 今天要回答的问题：**你是怎么排除掉其他原因、锁定真正原因的？**
> 答案浓缩成一句话：先按"原因排序"列嫌疑名单，再给每个嫌疑配一个**能证伪它的实验**，
> 用实验把假线索一条条踢出去，最后活下来的那个就是真凶——而且"踢出去"的理由也留了证据。

---

## ① 复现

**现象**：在检查台 ③「写入一条测试书籍」快速双击，浏览器控制台出现红色报错。

**复现步骤**（任何人可重跑：`node outputs/Day24/repro.cjs 8799`）：
1. 打开检查台 `check.html`，等 ② 读完 books/notes；
2. 用**真实鼠标**在「写入一条测试书籍」上双击（两次点击间隔 120ms，正常人手速范围内）；
3. 看 F12 控制台与 Network 面板。

**报错原文**（F12 Console，逐字）：
```
Failed to load resource: the server responded with a status of 409 (Conflict)
```
Network 面板同时可见同一标题发了两次请求：
```
POST /api/books → 201
POST /api/books → 409
```

**已尝试动作**（复现阶段的自我怀疑，防止把偶然当规律）：
- 换真实鼠标事件（`Input.dispatchMouseEvent`）而不是脚本里 `btn.click()`——排除"只有程序化点击才触发"；
- 用 `repro-boundary.cjs` 把双击卡在秒边界两侧再测一次——结果 `POST → [201, 201]`，**真的插进了两条测试书籍**
  （标题只精确到秒，`UNIQUE(user_id,title)` 对不同标题拦不住）；
- 对照实验：同样的双击打在 ⑥「确认删除」上，DELETE 只发出 1 次（见下文"排除"一节）。

---

## ② 定位（原因排序 → 每个原因的验证方法）

按可能性从高到低排嫌疑，逐个配实验：

| 排序 | 嫌疑原因 | 验证方法 | 结论 |
| --- | --- | --- | --- |
| 1 | **③ 按钮没有「请求中」保护**（点击后既不 `disabled` 也没有在途锁，第二次点击照样发请求） | 真人双击 → 抓 Network：POST 出现 **2 次**；读 `js/check.js` 对照 ⑤（⑤ 有 `patchSave.disabled = true`，③⑥ 没有）——三处行为不一致，指向同一个根因 | ✅ **真凶** |
| 2 | ⑥「确认删除」也没有禁用 → 会重发 DELETE → 服务端按契约回 404 | 同一 tick 连点两次 `#delete-confirm`（`repro.cjs`）：DELETE 出现 2 次、第 2 次 404；但换**真实鼠标双击**（`reachability.cjs`）：第一次点击同步把确认行换成「删除中…」，第二个鼠标事件落在文本上，DELETE 只有 **1 次** | ⚠️ 防御性加固，**真人不可达**，不作为现象依据 |
| 3 | 服务端幂等口径有问题（重复删除/重复收录不该报错） | 读契约 `api-contract.md` 第 1、8 项：409 duplicate 与 404 not_found 都是**设计要求**（"删过又删不假装成功"）；云函数按 `affectedRows` 如实回状态码 | ❌ 排除：服务端行为正确，不许动 |
| 4 | CORS / 网络层被拦 | Network 里请求全部同源、预检 204、无 `requestfailed` | ❌ 排除 |
| 5 | 错误提示层（Day 23 的 `friendlyError`）把正常路径误判成报错 | 界面文案显示「写入返回（输入错）：这本书已经在书架上了…」——归类正确，是"正常路径被重复触发"才产生了 409 | ❌ 排除 |
| 6 | 每页控制台都有一条 `favicon.ico 404`（与本次写入无关，但同样污染控制台） | `netstat`+Network：浏览器自动请求 `/favicon.ico` → 404，五个页面都有；项目里从未声明过 favicon | ✅ 独立小 Bug（余力加练修掉） |

**定位结论**：真凶是 **③ 写入按钮缺「请求中」保护**。这是前端 bug；
⑥ 同根因（也没禁用），但真人双击点不中它，只作防御性一并加固；服务端与契约层无罪。

---

## ③ 修复

改动都在 `js/check.js`（前端），**云函数零改动、无需重新部署**：

1. 新增两个在途锁 `writeBusy` / `deleteBusy`，注释里写清根因与证据；
2. ③ 写入：点击入口先 `if (writeBusy) return;` + `writeBtn.disabled = true`；
   失败才放行，成功路径保持禁用直到自动刷新（那 900ms 窗口里再点也不该再写一条）；
3. ⑥ 删除：`deleteBtn` 点击、确认行渲染、`doDelete` 三处都接同一把 `deleteBusy` 锁，
   并在点击瞬间压住确认/取消按钮——与 ⑤ 的既有做法对齐，三处行为从此一致。

余力加练（第二个、独立根因的低优先级 Bug）：五个页面补
`<link rel="icon" type="image/svg+xml" href="assets/img/gardenia.svg" />`（复用已有栀子花插画），
浏览器不再自动请求 `/favicon.ico`，每页一条的 404 红报错消失。

## ⑤ 顺手发现、今天不修（记录）

| 发现 | 说明 | 建议 |
| --- | --- | --- |
| ③ 写入成功后 900ms 自动刷新，会把反馈文案连同"写入成功"一起冲掉 | 双击场景下用户可能只看到空白 | 下次把"刷新后复现结果"做成刷新提示，而不是 reload |
| ② 只展示前 5 条 | 条数多时看不全 | 加"展开全部"或分页 |
| ⑤ PATCH 成功后「改之前」提示行不更新 | `patch-target` 仍是旧值（回归脚本 C8 一版就踩过它，改成从接口取当前值） | PATCH 成功后同步刷新 `patch-target` |
